## 2026-10-27 · 公式分类与发布范围（前端 2.39）

用户截图中的连续公式混合了 equation 与 text 分类，其中一条虽然保留了完整 LaTeX，却因被标为正文而回退到 OCR。上一轮将公式折叠为比较单元，解决长命令影响相似度，但遗漏了纯公式没有正文锚点的情况；这属于我们的处理边界。现在只对整个块都是带明确分隔符的公式加标点的情况，沿用已有完整公式选择；含行内公式的普通段落继续走字符映射，不全局更改解析结果。

显示端同时把连续独立公式归为一组，共用左对齐边缘。仅给块级 MathML 设置 text-align 在 WebKit 中仍可能居中，因此实测公式首部的几何位置，而不只检查 CSS 或 MathML 数量。真实教材只在本地验证，公开回归使用原创公式。

发布偏好已由用户明确改为只提供普通版。演示模式只作内部截图与测试，不对外分发 App；公开 README、打包脚本、历史 Release 下载、manifest 与 SHA256SUMS 一起调整。历史测试记录中的两版验收保留追溯意义，不代表当前继续分发演示安装包。

## 2026-10-27 · 解析完成不等于页面已绘制（前端 2.38）

本轮实际对照原 PDF、MinerU 原始输出、持久化本地 OCR 和选段预览：空集在 MinerU 中正确，本地 OCR 读成 @。此前校正按 LaTeX 命令的字面长度计算相似度，导致有多处长命令的正确段落落到阈值之外，未能校正。现在将已有整体选择语义的行内公式作为一个比较单元，同时保留公式的 UTF-16 原文区间；不全局替换 @，也不放宽不相关文字的相似度门槛。

文档准备的两个任务生成可复制文字与结构信息，PDF 原页图像仍由阅读器按需绘制。原实现离开相邻三页即释放位图，且绘制队列等待文字层，二者放大快速翻动的空白等待。本轮分离图像与文字任务、取消过期绘制，并保留有预算的近期页。没有把整书高分辨率图像常驻，也没有声称冷页可以零延迟；该缓存仅限当前阅读会话。

后续评审请覆盖慢文字层期间翻页、绘制中跳走后再返回、近期页复用、缩放清理和画布恢复。识别正确、选段校正正确、公式预览正确、原页绘制完成是不同的证据。

## 2026-10-27 · 用原文坐标和像素验证高亮（前端 2.37）

先前的原生高亮回归检查透明 Range 与高亮是否一致，但两者可能一起偏宽。本轮改以 PDF 原始字宽作独立基准，发现 macOS 通用字体受语言环境影响，画布和 DOM 的默认语言不一致；补齐语言与字宽校准，避免只裁短可见色块而保留错误命中范围。

扫描识别框不保证有行间空隙，尤其中文行内公式会增大框高。本轮遵循用户要求，用单次填充合并逐行高亮的可见区域，保持交叠处颜色一致。没有任意缩小识别框以制造间距；复制和提问原文保持。新增截图像素检查，而非仅数 DOM 色块。

## 2026-10-27 · PDF 目录不能只验证页码（前端 2.36）

论文目录的问题属于数据丢失：原 PDF 已有同页不同高度的目的地，导入时仅保留页序，后续 UI 无法还原。上一轮按不同章节是否到达不同页验收，遗漏同页多个小节和接近页底的标题。此次补充页内目的地、当前章节跟随、页底探针边界，以及旧书库自动升级；使用已有的归一化 `pdfY` 位置表示，不另建一套导航状态。

后续评审请区分“页码正确”“标题落点正确”和“当前章节提示正确”，并覆盖目录关闭 / 展开、缩放、跳转返回及重开。新增原创回归 `verify_pdf_outline.cjs` 与真实论文副本检查分别保留证据，公开仓库不含论文。

## 2026-10-26 · 从静态检查转向完整操作流程（前端 2.35）

本轮由独立代理执行功能验收，主代理修改。原先单元检查通过，仍在慢请求和跨窗口流程中发现重复书签、重复导入、书籍设置串写和旧检索结果可点；因此修复落在操作状态和数据归属，暂不迁移前端框架。书签除单窗口忙锁，还在状态写入互斥区以内容位置去重，客户端接收服务器最终列表。

PDF 的问题不能只概括为渲染失败。等高长页的三页预取正常，短页同屏却可能露出七页；使用单一高度占位，又使混合尺寸书的目标被邻页挤走。本轮根据视口计算绘制集合，并读取真实页几何建立占位，保留单页错误恢复和画布预算。真实扫描识别质量与图像渲染质量仍分别判断。

后续评审请优先看[功能验收说明](FUNCTIONAL_ACCEPTANCE.md)中的证据范围，重点检视操作进行中关闭窗口、切书、失败重试和多窗口同时更新。浏览器通过不代表实体全局按键、系统保存面板或任意云服务已被重新实测；文档明确区分这些边界。

## 2026-10-26 · 数学预览的结构与编号（前端 2.34）

此前只断言存在 math / mfrac，漏掉 `mstyle` 被转成 HTML span 后浏览器退出 MathML 的问题；这也使 annotation 源码变得可见。现在保留完整数学结构与安全的间距属性，并在浏览器核对命名空间及 annotation 的零布局尺寸。原始 MinerU 结果含文字空格，挤连来自本项目删掉 mspace 宽度；没有把这处显示问题归咎于 OCR。

另修复 texmath 对数组列格式空格的兼容，以及 `(15)` 等原页编号被 fancy_lists 转成列表、再丢掉起始值后全部显示为 1 的问题。仅在显示层规范化已解析数学与去重已知公式标签，复制、上下文和保存原文不变。历史回答仅重建显示缓存；不调用模型、不回写原始回答。下一轮请验证实际浏览器结构、数学间距和编号，不能再以存在 math 元素判定排版完整。

## 2026-10-26 · 原生 PDF 选区与空白页（前端 2.33）

上一轮主要验证扫描件 OCR，没有覆盖自带文字层的 PDF。实际 PDF.js 5.6.205 已通过 CSS 变量传递字形高度、横向缩放和旋转，但本项目没有消费这些变量，原生文字层错误沿用界面字号；这既是命中偏差，也是高亮溢出的根因。现按对应版本的 [官方文字层样式](https://github.com/mozilla/pdf.js/blob/v5.6.205/web/text_layer_builder.css) 补齐约定，原生 Range 继续负责拖选。

高亮参考 [Chromium 的 PDFiumRange 实现](https://chromium.googlesource.com/chromium/src/+/refs/heads/main/pdf/pdfium/pdfium_range.cc)：选择高度取 PDF 字体边界，合并同行相邻片段，保留分栏间距。单个 SVG 填充路径消除片段透明叠色，绘制不干预 Range 或复制。并未引入 PDFium 或声称所有特殊 PDF 都与 Chrome 逐像素相同。两种浏览器覆盖小型大写、密排行、分栏、旋转、缩放和双向指针拖选；私有原论文只用于本机比较。

新反馈的扫描教材空白页另查绘制链路：旧代码在失败后保留 loading、重复排队、未清理解码资源，并在整本超长容器上应用滤镜。现在成图后才替换位图，滤镜落到各页画布；去重并跳过过时预取，保留附近页面与现有选区、释放离屏解码资源，8 MP 限制单页画布。绘制失败显示可重试状态，画布丢失与回到前台时可恢复，原文字层和位置保留；旧 OCR 响应必须匹配当前页面实例。

请继续区分真实偶发消失与受控恢复测试：本机顺序浏览未稳定重现用户的同一空白截图，contextlost 使用模拟事件覆盖恢复分支，不代表强制触发了 macOS 的实际 GPU 回收。已用 529 页真实扫描教材隔离副本和原创长 PDF 验证快速滚动、跳页、缩放、失败重试与恢复。公开回归和安装包仍仅带原创资料，README 保持产品与安装说明。

## 2026-10-26 · 章节跳转回退（前端 2.32）

此前目录检查在跳转后主动调用 `readerFlush`，掩盖了真实使用中没有后续按键或滚动时不保存的问题。`navigate` 重建位置时丢失更新时间，恢复目标位置又会抑制滚动保存；轮询随后将服务器旧位置当成新进度，自动拉回原章。已用延迟返回旧状态的浏览器检查先复现，再为显式导航标记新时间，并在目标就绪后强制保存。

返回上一位置与查看原 PDF 复用同一导航路径，过期章节加载不再提交；同步在异步排版后再次核对当前位置，避免覆盖期间发生的新跳转。请后续检查跳转后静置、重开与双窗口，不要只验证即时目录高亮或用手动保存补齐产品行为。

主窗口默认展开目录，并将展开 / 收起统一更新到按钮状态；掌上窗口继续默认收起，避免覆盖小窗正文。复杂书籍仍使用隔离副本，公开检查与截图沿用原创资料。

## 2026-10-23 · 英文精细划词（前端 2.30）

用户实际阅读揭示了以前“连续六字符可选”验收的不足：英文墨迹框的字高差异、未单独定位的词间空格，以及反向拖选初始锚点，都可能造成多选 / 少选。已将英文字符渲染独立到 `ui/ocr-layer.mjs`，按行统一命中高度、明确空格位置，并让字符参与同一行的原生文本布局。没有引入自定义拖选状态机，也不需要重做已保存 OCR。

请后续评审区分原生选区、复制的校正文字和提问上下文三条路径；只看复制后的一句话正确不够。新检查在两种浏览器各执行 1008 次双向鼠标拖选，包含不同字高、标点、空格、缩放和字符内边界，同时断言未映射内容与标准区块混选、全文字缺失的整表顺序。真实教材的隔离副本也覆盖小字符与倾斜拖动，不再只用一条理想水平选区判断完成。

真实英文页固定 180 个端点案例从 95 个不一致降到 6 个，仍存在原始 OCR 框重叠 / 错位。请不要把透明文字层渲染修正等同于识别准确率提升，也不要把原创几何样本的全通过推广为所有教材精确无误。本轮不改变中文 Vision、原生 PDF 文字层或云增强协议。

最终两版 0.5.9 / 232 通过冻结服务检查并已保留数据升级。原生界面接口本轮可用，已在最终安装版英文扫描示例中实际执行正向、反向拖选及答疑引用核对，点击空白后操作条收起。构建额外发现新版 Python 的 SSL 运行时文件遗漏，已随包保留其原有策略并重新通过图像传输及导出检查；诊断代码不进入交付。

## 2026-10-21 · 后台快捷键的证据边界（前端 2.23）

用户已确认 0.5.1 可以拖动掌上窗口，但后台翻页失败。原来的状态只记录“登记了两个键”，不能说明按键实际送达。我们将登记和监听统一移到 `GetEventDispatcherTarget()`，接收入口参考 [HotKey 的原始实现](https://github.com/soffes/HotKey/blob/master/Sources/HotKey/HotKeysController.swift)，并增加登记返回值、收到次数、时间和 WebKit 错误。这个改动仍须以真实后台按键验收，不能仅凭采用同一个 API 就宣称问题已全部解决。

同时找到了可独立复现的问题：来自原生的翻页命令没有更新最近操作时间，另一窗口写入旧位置后，轮询可能在新位置保存前把小窗拉回。通过控制轮询先后顺序，Chromium 与 WebKit 的旧逻辑都从第 2 屏退回第 1 屏，新逻辑均保持第 2 屏。已把该场景加进公开回归脚本。

新增 Swift 测试确实经过 Carbon handler 和 WKWebView，但输入是程序构造的 Carbon 事件；它证明事件处理链路，不证明 WindowServer 对物理按键的分发。用户反馈已把“标题栏拖动”改为通过，“后台全局按键”仍待真实输入诊断。后续请继续区分登记、系统送达、前端执行和保存后的稳定位置。

后续实测中，用户按了一次指定组合键，但两个接收入口和新版原生小窗都没有通知。独占登记检查与安全输入检查未发现原因，不能把 dispatcher 改动写成已经解决了实际系统送达。现等待窗口内的键码记录，并把程序控制输入另存为对照，避免混作用户实测。

同时移除了快捷键完全硬编码的限制：用户可以在桌面设置中选方向键、P / N 或关闭。设置经现有偏好保存 / 同步，原生端只接受这三个预设。切换会释放旧绑定，后台功能关闭后普通窗口内翻页继续可用，跨窗口的按键设置变更也不重新分页。这个可配置能力不等于已经通过全局按键的实机验收。

完整安装包测试进一步暴露了状态确认问题：保存位置的回执会推进修订号，另一窗口已保存的偏好却可能尚未合并；下一次轮询又因修订号相等直接退出。现在比较实际共享字段，并保护尚未完成的本地写入。测试同时让另一窗口新增书签，验证它不会被本窗口随后的位置回执掩盖。当前原生集成检查已通过预设切换、禁用、Carbon 到 WebKit 的程序通知，以及快速关窗重开的竞争检查；物理后台按键的结论仍保持未通过。

## 2026-10-21 · 阅读交互缺陷复盘（前端 2.22）
